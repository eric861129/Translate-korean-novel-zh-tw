# 原稿、編碼與章節

只在新書盤點、建立工作目錄、檢討切分或確認解析異常時閱讀。正常續譯直接依 [日常操作](resume-and-delivery.md#自動保存合併與共用閱讀)；不每節重跑盤點或切分。

## 首次盤點

第一階段讀取兩份輸入的實際內容，確認哪份是韓文原稿、哪份是人工初翻版，並以人物、事件及對應段落確認是同一本書。不要憑「完整版」檔名判定內容或完整性。記錄來源路徑、檔案指紋、編碼、原稿總行數、字數統計、章節／分節數及最後一節；人工版若只涵蓋部分原稿，明確記錄可參照範圍，不據此縮減重譯範圍。盤點可掃描全書，但不等於把全書正文載入模型上下文。

只有韓文原稿時仍可執行 `inspect` 與 `plan`。本技能的重譯驗收目前需要人工版，`init --reference` 為必填；找不到時回報缺少輸入，不建立空檔或把原稿冒充人工版。

工具的 `auto` 支援帶 BOM 的 UTF-8、UTF-16、UTF-32，以及嚴格 UTF-8。無 BOM 的 UTF-16、CP949 等需在確認後明確傳入 `--source-encoding utf-16-le` 或 `--source-encoding cp949`。人工版使用獨立的 `--reference-encoding`。不使用忽略錯誤或替代字元的解碼。


```text
python -X utf8 <skill>/scripts/novel_pipeline.py inspect --source <韓文.txt> --reference <人工版.txt> --details
```

`inspect` 不寫入。輸出大時將閱讀拆成必要範圍；不要向使用者貼整份小說。至少核對開頭、結尾、序章、番外／後記位置、章號變動與疑似跳號處，並搜尋原稿中未被解析器辨識的標題形式。

## 字數口徑與盤點報告

韓文以空白分隔的 `eojeol` 不等於中文字數，也不等於語言學上的單字。**所有翻譯工作量上限都用 `chars_with_spaces`**；不要以中文譯稿長度、檔案位元組或固定字數／token 倍率安排任務。來源包的 MiB 僅控制實體儲存大小，不用來安排一次翻譯量。

`inventory` 的計數先用 NFC 合併可組合字形，保留原稿及原始位元組指紋不動。四個指標分別是：

| 欄位 | 意義 |
|---|---|
| `chars_with_spaces` | 含空白、標點、韓文及其他文字的 Unicode 字元；排除換行字元 |
| `chars_without_whitespace` | 去掉所有空白後的字元，供人比較篇幅 |
| `hangul_characters` | 韓文字元含可辨識字母，不含漢字、數字或標點 |
| `eojeol` | 按空白切分的非空單位數，只作輔助 |

`file_metrics` 涵蓋全檔；`body_metrics` 涵蓋解析後的非空內容區塊，排除標頭與已識別版面標記，仍包含前置文字及場景分隔。`preamble_body_chars` 單列前置內容，不能自動扣成廣告。舊欄位 `characters` 是解碼後原始字元數，含換行，不用來套批次上限。

盤點回報包含：全檔與內容字元數、前置內容字元數、編號分節／特殊分節數、編號分節最小值／中位數／平均／P90／最大值、超過小段與批次上限的分節數，以及疑似未辨識標題。`inspect` 的 `over_6000`、`over_12000` 是預設參考門檻；自訂上限時按 `--details` 的分節資料重算。分節不等於獨立章號，`1화 ... (1)` 與 `(2)` 必須分別計數。

`all_section_distribution` 另列所有分節的分布，`largest_sections` 列出最長五節，避免只看編號章節漏掉超長番外或後記。`structure_warnings` 提醒過長的前置／非編號分節，仍須回讀才能判定格式是否有問題。

前置內容異常長、正文被歸到前置分節、單一分節占了大量全書篇幅時，先查解析器；不能把錯誤索引拆小後直接翻譯。P90 採排序後向上取第 90 百分位位置，只描述章長分布，不預測翻譯時間。

## 拆分策略與起始設定

| 方法 | 評估 |
|---|---|
| 固定每次 N 章 | 易理解，但章長差異可能讓工作量失控；只用來描述範圍 |
| 每滿 N 字直接截斷 | 工作量穩定，卻可能切斷句子、對話或場景；不採用 |
| 字元預算加語意邊界 | 預設採用。先保留原分節，再在合適場景／段落界線形成小段、內部工作單位及全書交付批次 |

採三層規劃：`c` 是一次譯寫／回查的小段，目標 4,000、上限 6,000 字元；`b` 是批內可保存的工作單位，最多 3 小段且合計不超過 12,000 字元，單一 `b` 不跨原分節；`d` 是向使用者交付的全書進度批次，長篇預設以約 10 批為目標，可涵蓋多個 `b`、多個原分節。任何小段或工作單位上限先達就收尾，不為湊滿數字拆句。短分節可以單獨一個 `b`；一個長分節可以橫跨數個 `b`。

全書交付批次先以原文字元預算分配，第一批的規劃權重為後續單批的一半，容納前置審查、首個正文小段試譯、名詞表與文體校準；後續各批盡量等量，但只在完整原分節結尾切開。同一超長分節的多個 `b` 留在同一 `d`，讓整節驗收能在該交付批次內完成。若非空原分節不足 10 個，就只產生可完整驗收的交付批次，不為湊數建立空批或切斷分節。這是來源量分配，不是預估每批耗時等量。既定譯名可在後續重用，減少重複決策；新人物、指代與語意仍逐段核對，速度不保證線性提升。

第二階段以 10 批為規劃起點，再按總字元量、章長分布及完整分節調整 `--delivery-batches`。短篇可減少批數，長篇優先維持約十批；若需明顯偏離，說明來源量與切點理由。不要因內部 `b` 很多就增加數百個交付批次，也不要為壓在十次回覆內而放大小段、略過校對。保存實際批數與每批來源範圍，第三階段依定案計畫執行。

首次先審查來源前置文字，再做第一個正文小段作試譯。序章屬正文；空標題或已確認的來源廣告不能充當試譯。試譯後先保存並核對，再繼續第一個 `d`；不把試譯另算成第 11 個交付批次。

這些值用於控制校對量，不是模型能力保證。首次試譯後看實際改錯密度、主詞與專名問題、輸出完整性及上下文餘裕；複雜段落可降為目標 2,500、上限 4,000、每個 `b` 8,000／2 小段。一般設定可沿用數個 `b` 再評估；不要只因一次譯文流暢就放大。須為韓文、譯文、逐段對應、詞庫及回查保留空間，來源字元上限不代表全部上下文預算。一個 `d` 往往大於單次上下文或輸出容量，實際可能跨多次接續；不能把「10 個交付批次」說成「10 次模型回覆」。

## 產生候選批次

```text
python -X utf8 <skill>/scripts/novel_pipeline.py plan --source <韓文.txt> --target-chars 4000 --max-chars 6000 --batch-chars 12000 --max-chunks 3 --delivery-batches 10
```

未給 `--output` 時只輸出 JSON，不建立工作目錄。建立書籍工作目錄後，用相同編碼及 `--heading-pattern` 加上 `--output <工作目錄>/batch-plan.json` 保存，工具拒絕覆寫既有檔案。計畫綁定原稿指紋、編碼、解析模式和切分參數，包含小段 `c000001`、工作單位 `b00001` 與交付批次 `d0001` 的 ID、字元數及來源範圍；它們都不作小說標題。`summary.delivery_batches` 是使用者看到的交付批次數；舊欄位 `summary.batches` 及頂層 `batches` 仍表示批內工作單位數與明細，不能解讀成需要 500 次交付。

候選切分方式：

1. 已在 6,000 上限內的剩餘分節保留完整；較長分節在目標附近，依序考慮場景、空行形成的段落界線、完整原文區塊界線。
2. 一個內容區塊是非空原文行，未必是一整段。工具無法理解對話；代理必須核對切點前後，必要時在預算內移動界線，讓開場、回應、動作結果盡量一起處理。
3. 同一原文區塊只能分配給一個小段，全部小段的來源範圍依序、無重複且無缺口。前後文另讀，不加入本段的翻譯覆蓋範圍。場景符號仍保留。
4. 單一原文行超過上限時，工具保留全文並標記 `requires_manual_split`，相關批次 `blocked: true`。這不是允許超量翻譯；先確認是否匯出格式把整章壓成一行，再完善可追溯的句段解析。現有工具不支援半行的驗收，不能手改原稿或憑空增加區塊 ID 來通過。
5. 第一個非空、非前置分節的小段獨立為 `pilot` 工作單位；其他按原分節、字元與小段數上限分組。再按來源量把連續的工作單位歸入交付批次，只在原分節邊界切開。第一批含前置審查與試譯，但不另增加交付批次；交付批次數不等於章數、模型呼叫次數或承諾的工作天數。

代理可在翻譯前核對並修正候選計畫，修正後重新計算相關字元數、區塊數、`source_sha256 = digest(canonical(blocks))` 與批次歸屬，逐一驗證原文區塊恰好覆蓋一次，且所有未阻塞批次都符合上限。先定案才保存計畫指紋；`plan` 的機械切點不冒稱已完成語意審查。

已有進度時不直接重跑覆寫計畫。第一個 `d` 完成後可依實際校對負荷檢討未完成交付批次的切點，但工具不會自動依名詞表成熟度重分配；調整時保留舊計畫，以新計畫的原文分節、區塊 ID 範圍與指紋對應既有稿，更新進度中的計畫指紋及 `d` 歸屬；不能用新產生的 `c`／`b`／`d` 編號猜測沿用。有效整節收據仍由 manifest 判定，不能因重分批就清除。

例：7,000 字元的一章可依段落分為約 4,000＋3,000，放進同一個 `b`。18,000 字元若恰有合適切點，可分 4,000＋4,000＋4,000＋6,000，再分為 12,000 與 6,000 的兩個 `b`，仍可同屬一個 `d`。第一個正文試譯小段會獨立成一個 `b`，實際數量依原文切點計算，不能只用總字數除以 12,000 宣稱精確的 `b` 或 `d` 數量。

## 解析器的能力與邊界

預設辨識：

- `1화 기회 (1)`、`< 1화 기회 (2) >`、`127화 종장(終章) (完)`。
- 同形式標頭的 `(오류 수정)` 註記。
- 單獨的 `서장`、`프롤로그`、`에필로그`、`종장`、`외전`、`후기`、`작가의 말`，可帶數字括號。
- 當前分節相同標頭後的 `끝` 為結束標記；不同分節的結束文字不靜默刪除。

其他形式需提供 `--heading-pattern`，以 `fullmatch` 比對去掉外層尖括號的標頭，可使用 `chapter`、`title`、`part`、`kind` 命名群組。例如 `외전 1화 귀환` 與普通標頭並存時，先為該書設計涵蓋兩者的解析模式並用 `inspect` 驗證。`kind` 可標示番外；番外獨立章號若需不同中文標頭規則，應先調整解析／驗證器，不能改動原稿遷就工具。

無法判定整本結構時，不開始大量翻譯。未知格式的行會留在內容區塊，這能防止文字消失，但不保證章節邊界已辨識正確。

## 分節與內容覆蓋

- `s0000` 起的 ID 表示原稿順序，不等於出版章號，也不以中文譯名命名。
- 每個非空內容行取得 `s0001:p0001` 形式的 ID，保留原始行號；此粒度只供核對，不限制中文排版。
- 空行與明確長分隔線不當故事內容；分隔線及配對結束標記仍留在 `format_lines` 可追溯。
- 第一個標題前的文字建立 `preamble` 分節。商店廣告可以經審查後排除；書名、引文、作者附記或故事前言不能只因位於前面就排除。
- 章節中的 `* * *` 場景切換仍是內容，需對應到譯文的場景分隔。
- 章號跳動、同名跨章或分節號延續，先記為原稿現象。原稿 `74화 ... (4)` 後接 `75화 ... (5)`，不能只憑規律重編為第 74 章。

「提供原稿完整覆蓋」與「官方出版全集完整」是兩個不同判定。工具只能協助前者。

## 來源包與按節讀取

原稿保持唯一原始來源；`manifest.json` 的 v2 格式只保存章節中繼資料、收據及來源包定位，不再內嵌全書 `blocks`／`format_lines`。解析結果以 UTF-8 JSONL 存在 `context/source/<generation>/part-0001.jsonl`，每行是一個完整原分節，仍保留原始行號、標頭、版面標記、內容與所有 `s`／`p` IDs。人工版不另外拆檔。

- 每包目標 **2 MiB（2,097,152 bytes）**，一般上限 **4 MiB**、最多 **100 個原分節**。大小依實際 JSONL 的 UTF-8 位元組計算，包含索引資訊；不是兩百萬韓文字元。
- 順序加入完整分節，達目標便換包；加入下一節會超過上限或節數已滿時先換包。尾包可較小，不切斷分節、不為湊滿而重排。單一分節超過 4 MiB 時獨立成包並標記 `oversized_section`，先回查是否解析異常；確認後仍依 `c` 上限翻譯。
- 每節保存包名、UTF-8 byte offset、長度與 SHA-256；包另有整包指紋。日常操作讀取所需包、檢查指紋後只解碼當節，不以 `read_text().splitlines()` 展開全包或反覆解析整本原稿。同一操作最多保留兩包與四節解碼結果。
- 來源包、原分節 `s`、翻譯小段 `c`、工作單位 `b`、交付批次 `d` 各有不同用途；包數不必等於約十個 `d`，更不建立每個 `c` 或每節一份韓文檔。TXT 對話空行與中文分節產物依既有流程處理。
- 每次操作仍串流讀取兩份原始輸入並核對完整指紋。首次或索引／規則失效時重新解析原稿並核對全部來源包；有效快取才免重複解析。`validate` 與最終交付始終完整核對原稿、索引及來源包。

`context/` 全部可由原始輸入及權威工作檔重建，保持 Git 忽略；Git 保留精簡 manifest、原稿、人工版、計畫、詞庫、進度與譯稿證據。重新 clone 後若缺來源包，先執行 [rebuild-source](maintenance.md#來源格式遷移與重建)，不能改索引指紋迎合損毀快取。來源包不手改、不當成新版原稿，也不另存重複 TXT 副本。

## 對齊人工版

人工版可能多出流水章號、合併分節、缺少標題、使用中文數字或含舊譯錯字。用事件、對話、獨特專名與原文段落定位同一段，不以兩檔行號或單一章號直接配對。

在 `terminology.jsonl` 的證據中記下人工版位置；必要時在個別 mapping 加入 `reference_evidence`。定位資訊作為參考，不把人工版當作原文逐段覆蓋的依據。

## translation-work 目錄架構

以下為每本小說的 v2 工作架構。輸入檔名僅為示意，沿用實際路徑；原稿與人工版可位於其他目錄，不為符合架構圖而搬移或改名。`<generation>` 是工具產生的來源包版本識別碼，實際位置由 `manifest.json` 記錄。

```text
<小說目錄>/
├─ 韓文原稿.txt                         原始輸入，保持原樣
├─ 人工初翻版.txt                       參考輸入，保持原樣且不另外拆檔
├─ <書名>-繁體中文重譯完整版.txt         全書驗收後組裝的唯一最終版
└─ translation-work/
   ├─ manifest.json                    雙輸入資訊、原稿索引、來源包定位與收據
   ├─ batch-plan.json                  交付批次 d、工作單位 b、小段 c 的範圍
   ├─ batch-progress.json              真實進度、續譯位置與最終輸出路徑
   ├─ terminology.jsonl               名詞表、譯名依據與人物口吻
   ├─ continuity.jsonl                情節狀態與前後文摘要
   ├─ reviews.jsonl                   校對問題與修正紀錄
   ├─ book-review.json                全書複核完成後的聲明與十項評分
   ├─ context/                        可重建的衍生資料，Git 忽略
   │  ├─ source/
   │  │  └─ <generation>/
   │  │     ├─ part-0001.jsonl         約 2 MiB，多個完整原分節合存
   │  │     ├─ part-0002.jsonl
   │  │     └─ …
   │  ├─ reference/
   │  │  ├─ index.json                人工版稀疏行號索引，不複製正文
   │  │  └─ search-cache.json         有上限的搜尋位置快取，不逐詞開檔
   │  ├─ s0001.json                   本節所需依據與來源引用，不重複保存韓文正文
   │  ├─ s0002.json
   │  └─ verification-cache.json      機械驗證快取
   ├─ pipeline/                       僅舊平行任務保留，草稿與證據納入 Git
   │  ├─ state.json                   舊角色、派工識別及停用狀態；不是正式進度
   │  ├─ slot-01.json                 固定槽位的初譯與中斷保存資料
   │  ├─ …
   │  ├─ slot-10.json                 舊槽位原樣保留，切回單代理後不再重用
   │  └─ assist.json                  舊查證資料，未決部分由同一 Session 接手
   ├─ chunks/                         翻譯小段產物
   │  ├─ c000001.input.json           譯文輸入與逐段核對紀錄
   │  ├─ c000001.txt                  小段中文譯文
   │  ├─ c000001.map.json             小段原文與譯文對應
   │  └─ …
   ├─ sections/                       合併後的完整分節產物
   │  ├─ s0001.txt                    完整分節中文譯文
   │  ├─ s0001.map.json               整節原文與譯文對應
   │  ├─ s0001.review.json            整節複核、評分及實際完成的連讀紀錄
   │  └─ …
   ├─ drafts/                         需要落盤的待提交稿，保留 Git，按需建立
   │  ├─ c000001.input.json           小段草稿或待驗收修訂，不代表已通過
   │  ├─ s0001.review.input.json      尚未正式保存的分節複核輸入
   │  └─ legacy/                     整理舊工作時保留的獨有修訂／查證，不新增日常版本
   ├─ tmp/                            可重建暫存與已提交副本，Git 忽略
   │  └─ s0001.review.input.json      已核對正式存檔存在的輸入副本
   └─ .migration/                     舊格式遷移時才產生，Git 忽略
      └─ manifest-v1.json             遷移前的索引備份
```

- **建立時機**：準備階段只建立下節列出的必要資料；`context/sNNNN.json`、驗證快取及人工版 `reference/` 按需產生，後者依 [人工版搜尋與擷取](resume-and-delivery.md#人工版搜尋與擷取) 使用。`chunks/`、`sections/` 內的檔案隨實際翻譯及複核保存。全書聲明與最終 TXT 在完成對應驗收後才產生，不照架構圖預建占位成果。暫時的 `.writer.lock` 由工具管理，未列入圖中。
- **分包與翻譯層級**：來源包數量依實際大小及原分節數決定，和約十個交付批次分開計算；`b`、`d` 記錄於計畫及進度，不另建每批資料夾。完整分包界線、大小上限及例外見 [來源包與按節讀取](#來源包與按節讀取)。
- **舊平行資料**：新書不建立 `pipeline/`。既有目錄可能含不可重建的初稿與查證，依 [舊稿交接](parallel-workflow.md) 停用派工並保留 Git；只將 `state.json` 當作舊稿定位，不據此推定正式進度或重切計畫。
- **版本控制**：原稿、人工版、最終譯本及續譯依據保留 Git，包括 `chunks/`、`sections/` 的輸入、對應與複核檔，以及 `drafts/` 尚未接收的工作。`context/`、`tmp/` 與 `.migration/` 忽略 Git；重新 clone 後缺來源包時，依 [來源重建流程](maintenance.md#來源格式遷移與重建) 處理。

### 生成檔案的位置與命名

- 開始寫檔前確認本書既有 `manifest.json` 與工作目錄絕對路徑，所有命令明列該 `--work`。不要依目前 shell 目錄推測小說位置，不在 Repo 根目錄另建 `translation-work`。原稿與既有人工版沿用原位置。
- 日常提交優先使用 `--input -`，由工具驗證後保存固定名稱。小段正式輸入是 `chunks/cNNNNNN.input.json`；分節正式複核是 `sections/sNNNN.review.json`，標準／精簡 JSON 與檔案／stdin 輸入一律相同。不要為每次呼叫另建 JSON 或 Python／PowerShell 腳本。
- 必須保存未提交、未驗收或中斷的工作時，寫入 `drafts/cNNNNNN.input.json` 或 `drafts/sNNNN.review.input.json`；不完整正文可用 `drafts/cNNNNNN.txt`。固定 ID 對應固定檔名，不按每次嘗試增加 `v2/final/fixed`。修訂既有正式稿時先在 `drafts/` 編輯，再由工具驗證及保存，不先覆寫有效正式輸入。
- `tmp/` 只放可重建的查詢輸出、無唯一正文的臨時腳本，以及確認已保存到正式產物的提交副本。譯文、評分、主詞判斷或查證若尚無正式存檔，仍放 `drafts/`；不能因副檔名是 JSON 就當成暫存。兩個目錄皆按需建立，不再按章節、代理或批次建立子目錄。
- 成功提交後，先讀回工具回傳的正式 `input` 路徑確認內容，再依原任務授權處理本次重複副本；優先使用 stdin，避免先建立副本。不要每個小段都重掃全書來整理檔案。`drafts/legacy/` 僅用於一次性的舊檔歸位，保留原內容及可辨識的原檔名；其存在不代表該節待翻譯，是否沿用仍看正式進度與最早缺口。
- 小說根目錄不放 `sNNNN.review.input.json`、提交腳本或其他工作 JSON；`translation-work` 根目錄只放架構圖所列全書共用檔，不放逐節提交副本。`chunks/`、`sections/` 留給固定正式產物。
- 整理既有檔案時先核對用途、引用與同名檔；只有已確認正式存檔包含其內容的副本可移到 `tmp/`。移動前後核對位元組雜湊，不覆蓋同名內容、不自動刪稿。既有特殊路徑或獨有修訂不能只靠檔名批次搬移；遇到仍在寫入的工作，留待該任務保存點處理。

### 舊工作檔的用途與保留判斷

| 檔案類型 | 用途與整理方式 |
|---|---|
| `chunks/cNNNNNN.input.json/.txt/.map.json`、`sections/sNNNN.txt/.map.json/.review.json` | 正式譯文、對應、評分與校對依據，保留固定位置與 Git。不能因 JSON 很多而整批忽略或刪除。 |
| `cNNNNNN-parallel-details-input.json`、`*-parallel-review-input.json`、`pipeline/review-c*.json` | 舊詞條／草稿查詢參數，只記派工 ID、版本與欲查詞條，查詢結束後可清理；不是正式詞庫或查證結果。 |
| `parallel-assist-request.json`、`*-assist-resolve.json`、`*-accept-input.json` | 舊查證問題、採納判斷或修訂輸入。先核對 `pipeline/` 或正式小段的 `parallel_review` 是否已保存其內容；未確認完整採納時保留到 `drafts/legacy/`。 |
| `.codex-draft-submit-*.json`、`*.translation-draft.txt` | 初譯或中斷稿。已接收草稿可依正式紀錄的草稿指紋或內容確認重複；不能只因代理已停用就刪除。無法確認時保留。 |
| `sNNNN.review.input.json`、`.tmp-review-*`、`.tmp-submit-*`、修訂版本輸入 | 提交副本或重試資料。核對正式輸入、map、評分與連讀紀錄後才判定重複；含獨有文字、未保存判斷或格式錯誤但可恢復的稿件，放 `drafts/legacy/`。腳本可能內嵌譯文，不能全部視為空殼。 |
| `pipeline/state.json`、`slot-*.json`、`assist.json` | 舊派工與初稿證據，保留既有位置，避免破壞正式紀錄的引用；不再建立新派工。 |
| `context/`、`.migration/`、`tmp/` | 快取、本機遷移備份與已確認可丟棄的暫存。Git 忽略；不要為減少 Git 變更反覆刪除可重用的來源包。 |

## 建立工作目錄

第一階段確認兩份輸入與原稿結構後，第二階段使用該書獨立的工作目錄。新工作執行：

```text
python -X utf8 <skill>/scripts/novel_pipeline.py init --source <韓文.txt> --reference <人工版.txt> --work <小說目錄>/translation-work --title <書名>
python -X utf8 <skill>/scripts/novel_pipeline.py plan --source <韓文.txt> --delivery-batches <定案批數> --output <小說目錄>/translation-work/batch-plan.json
```

`init` 預設建立 v2 精簡索引、約 2 MiB 來源包、三份空 JSONL 與 `sections/`；不會自動建立計畫或進度。`--source-layout inline` 僅供明確需要舊 v1 格式的相容情境。`plan` 要使用與盤點、索引相同的來源編碼、解析模式及定案切分參數。代理須在建立 Goal **之前**補齊並讀回下列資料：

| 必要檔案／目錄 | 第二階段結束時的內容 |
|---|---|
| `manifest.json` | 正確的雙輸入路徑、指紋及原稿結構索引；v2 保存來源包目錄與逐節位元組定位 |
| `context/source/<generation>/` | v2 的約 2 MiB 衍生來源包；覆蓋全部原分節且指紋核對成功 |
| `terminology.jsonl` | 已核實的初始專名；尚無核實資料時可為空檔，名詞表於翻譯中逐步完善 |
| `continuity.jsonl`、`reviews.jsonl` | 有真實依據的既有紀錄，或合法空檔；不預填敘事、評分或校對成功 |
| `batch-plan.json` | 全書 `d`／`b`／`c` 的定案範圍、字元量與來源指紋 |
| `batch-progress.json` | 真實檔案指紋、執行模式、最早未完成位置及唯一最終輸出路徑；新工作為 `phase: prepared` 且沒有已完成小段，續譯保留實際階段 |
| `sections/`、`chunks/` | 已建立、可供後續保存的工作目錄；新工作不放占位譯稿 |

進度初始格式依下節；持續保存規則見 [工作資料與完成狀態](resume-and-delivery.md#工作資料與完成狀態)。最終路徑預設 `<小說目錄>/<書名>-繁體中文重譯完整版.txt`，保存在 `final_output.path`；使用實際絕對路徑，不能指向輸入或工作目錄內。先檢查檔名衝突，整個流程沿用同一路徑，不為每批另產一份完整版。

進入第三階段前，讀回必要檔案，核對 manifest 與計畫的原稿指紋、解析設定一致，計畫原文區塊依序且恰好覆蓋一次，`d` 完整涵蓋其 `b`／`c`，人工拆分阻塞已解決，進度中的來源、人工版及計畫指紋均為實際計算結果。新工作的游標取計畫第一個 `d`／`b`；續譯則以有效檔案證據重算。這是結構與可恢復性檢查，不代表已閱讀或翻譯全書。此時不建立假的 `book-review.json` 或全書完成收據。

既有目錄會拒絕初始化，`plan --output` 也拒絕覆寫；續譯先驗證並沿用現有索引與計畫，只補缺少項目，不清空有效紀錄或把進度重設為未開始。原稿與人工版保持原樣。既有主工作階段正在翻譯時，不另建相互競爭的整本翻譯工作。

## 初始進度

新工作的初始進度示例；路徑、指紋與第一個 `d`／`b` ID 須以實際資料取代，不能照抄說明文字。下例為已獲指示、待建立 Goal 的全書工作：

```json
{
  "schema_version": 1,
  "source_sha256": "原稿整檔指紋",
  "reference_sha256": "人工版整檔指紋",
  "plan_sha256": "已定案 batch-plan.json 的檔案指紋",
  "execution_mode": "full_goal",
  "phase": "prepared",
  "active_delivery_batch": "d0001",
  "active_batch": "b00001",
  "chunks": {},
  "style_profile": {},
  "final_output": {
    "path": "唯一最終 TXT 的實際絕對路徑",
    "sha256": null
  },
  "section_review": {},
  "book_review": {"completed_batches": [], "next_batch": "b00001"}
}
```

`execution_mode` 記錄 `full_goal`、一般全書任務 `full` 或範圍限定的 `batch`；限定範圍另存 `requested_scope` 的實際來源／批次 IDs。此欄位只是紀錄，不能取代使用者授權或證明 Goal 已建立。`phase` 隨實際工作改為 `translating`、`finalizing`、`delivered`；不能單靠此欄位判定完成。舊進度缺少這些欄位時，依原始任務與證據補齊，不重設為 `prepared`。

第二階段完成時簡要回報雙輸入、原文字元數、實際 `d` 數、工作目錄及唯一最終路徑。準備工作檔與批次覆蓋核對完成後，已獲 Goal 指示者才依 [Goal 操作](resume-and-delivery.md#goal-建立與逐批接續) 建立或沿用目標；其餘按原授權範圍進入翻譯。
